# 上下文组装与来源记录 V0.1

已完成独立开发。开始前重读 本机 local.paths.json 的 harness_note 所指原始笔记，
重点参考回合调用前预检、静态/动态指令分离、作废结果清理和事件与对话隔离。

## 这轮改变了什么

每次调用前，由程序组装当前会话的有效上下文：
静态系统指令 → 保留的历史消息 → 当前确认草稿的数据块 → 本轮用户输入。
这里只决定哪些数据进入模型，不定义心理字段、评分或临床规则。

草稿必须同时满足：属于本会话、状态 CONFIRMED、确认版本与当前版本相同。
修改后未重新确认的草稿、已拒绝草稿都不注入。
多个不同编号的确认草稿会同时注入；新建编号不自动替代其他编号。

草稿作为 user 角色的 JSON 数据传入，不拼入 system 指令，也不写入原始对话历史。
系统指令明确将其视为用户确认的数据，而非专业结论或执行授权。
本轮提示词版本为 emotional_chat_v0.4。

## 如何处理旧回复

每条成功生成的助手回复都会记录其依赖的草稿编号和版本。
下一次组装时，若依赖已经修改、撤回或不再确认，排除这条历史助手回复。

这是保守的整条回复排除，不做句子级修订。原始用户消息照常保留，
无草稿依赖的普通助手回复也保留。模型的输入过滤不会删除可见聊天历史。

因此，撤回草稿表示停止后续自动使用该草稿，并排除依赖它的旧回复；
原始用户消息若本来就写过同样内容，仍可能出现在输入中。
要删除会话内容，使用 /clear 或 DELETE /sessions/{id}/messages。

## API 与来源记录

发送消息的响应增加 context_manifest，包含：
- builder_version、prompt_version；
- session_id、组装时的 session_revision、request_id；
- model_message_count 和 character_count；
- sources：系统指令、历史消息、本轮输入、确认草稿的来源；
- excluded_history_indices：因草稿依赖失效而排除的历史助手消息位置。

模型消息序号包含 provider 添加的系统消息（序号 0）。
历史位置对应当前会话 messages 的零起始下标。
多个草稿共用一个数据块时，来源记录可以指向同一个模型消息序号。

| 方法与路径 | 用途 |
|---|---|
| GET /sessions/{id}/context | 最近成功调用的来源清单；没有则为 null |
| POST /sessions/{id}/context/preview | 用 {"content":"下一条输入"} 预览当前来源与长度，不调用模型、不提交会话 |

预览是本机开发诊断。实际调用仍会在会话锁内重新组装，不直接信任先前预览。
失败不会覆盖最后成功记录；重放旧请求返回该请求原来的来源清单，不重新执行模型。

## 预算、并发和数据

字符预算包括静态指令、筛选后的历史、草稿 JSON 和包装文字、本轮输入。
超限在调用模型前返回 413，不自动截断或总结。字符数量不是精确 token 数量。

组装与调用、草稿修改沿用同一会话锁。修改会等待当前轮次结束；
需要立即中止时先调用运行取消接口，再修改草稿。
只有成功返回的回复才提交来源与依赖。清空会话同步清除最后来源、依赖、草稿和缓存内容。

诊断只记录编号、版本、长度、条数和过滤位置，不记录正文或 Key。
数据仍仅在进程内存中，热重载或重启会清空；联调时等待代码重载稳定后新建会话。
