# Personal Emotional Agent：盛蕾负责范围的产品机制研究与开发建议

调研日期：2026-11-04。范围：可穿戴数据接入、个人基线与变化分析、安全支持、Agent 联动。本文为研究与开发提案，未修改项目代码，未进行设备实测或临床验证；主任务核实仓库 ae97cac 为 Python FastAPI runtime，暂无前端；目前单用户、本地、无身份认证，内存状态加显式快照。下文 Web 交互为新增客户端提案，并非已有界面。官方资料中的产品功能不等于我们的已实现能力。

> 本文保留调研阶段的候选思路；实施范围、字段与排期统一以 [详细开发方案](shenglei-development-plan.md) 为准。研究不是已审核心理规范。

## 1. 建议先交付什么

先完成一条可重放的闭环：**模拟设备数据进入 → 数据质量检查 → 与个人历史比较 → Agent 提出带证据的询问 → 用户纠正 → 更新本次解释及以后建议 → 必要时进入安全支持流程**。然后选择一个真实设备来源接入。不要把「心率偏高」直接翻译成「你焦虑了」，也不要把设备授权成功当成持续、有质量的数据已到达。

Web MVP 可首先支持手动记录和明确标记的模拟数据；Oura 云 API 是有合适设备和账号时的候选；Apple HealthKit、Android Health Connect 的直接读取需要对应原生端集成。实际硬件选择应由现有设备、用户系统、地区可用性和数据授权可行性决定，本研究不建议仅为 Demo 购买设备。

## 2. 已核实的官方机制与可借鉴之处

| 来源 | 官方事实/产品自述 | 对本项目的含义（我们的推断或建议） |
|---|---|---|
| Oura Daytime Stress | 用心率、HRV、运动、平均体温分析生理压力；对比每日更新的个人基线；生理结果不一定与主观感受一致。运动和缺测可能产生空白，情境关联不能证明原因。[S1] | 对外使用「身体信号变化」，向用户询问情境；保留未知与缺测；不建立通用焦虑阈值。 |
| Oura Resilience | 以过去 14 天的日间压力、日间恢复、夜间恢复反映中期平衡；要求窗口内至少 5 天完整数据，新用户建立估计可能至少需 10 天。[S2] | 「当下变化」与「近期趋势」分开呈现；冷启动不是异常。不要将其指标改名为心理韧性诊断。 |
| Oura API | 官方入口要求账号与 API 应用，多用户应用使用 OAuth；V1 已移除，使用 V2。[S3] 授权文档支持明确 scope、state、PKCE；refresh token 为单次使用；需非空 User-Agent。[S4] | 后端处理凭据、刷新与并发锁；首版最小权限；不要把密钥放进前端或将旧 PAT 教程当作现行方案。 |
| Apple HealthKit | 按数据类型请求读写权限，需原生应用能力配置和用途说明；为保护隐私，应用不能直接知道读取权限是否被拒绝，空结果不能等同用户拒绝。[S5] | 普通网页不能凭一个「连接 Apple Health」按钮直接取得手机健康库；需要原生桥或明确的导入路径。UI 使用「暂未读到数据」，保留多种可能原因。 |
| Android Health Connect | 读取走 Android SDK；后台读取需要额外权限，历史读取也存在权限边界；累积步数建议使用聚合能力避免多来源重复计算。[S6] | 原生 Android 适配器处理权限和历史窗口；不把后台持续同步当作默认能力；数据合并需显式规则。 |
| Wysa | 官方描述 SOS 入口、会话中识别困扰并引导本地危机资源。[S7] FAQ 同时明确不是紧急援助服务；向教练共享聊天有授权选择。[S8] | 借鉴「用户主动求助 + 风险触发 + 外部支持入口」，不能宣称 AI 可以完成救援或替代专业服务。 |
| Wysa SOS 研究介绍 | 官方观察性报告描述了 AI 提示后由用户确认，以及用户主动进入 SOS 两条路径。[S9] | 借鉴确认机制，不将其统计比例当成本项目识别准确率，也不能把确认作为紧急资源显示的前置门槛。 |

**来源限制：**本次能读取 Oura 产品支持页、API 入口及授权文档，但 V2 动态接口文档未提取出可读 schema。因此没有把网上第三方整理的 `daily_stress`/`daily_resilience` 字段、单位、刷新频率或细粒度曲线可用性写成已验证事实。Oura App 能显示某图表，不代表开放 API 提供同样粒度。实施前必须拿到当前官方 schema 和脱敏真实响应。Apple 标准 URL 为动态页面，授权正文通过官方同页的检索版本取得。没有验证大陆网络、特定国产手机、具体手表、商店分发或第三方模型服务条款。

## 3. 数据接入：一个统一契约，多个适配器

以下均为本项目设计建议，不是任何厂商现成 API。

### 3.1 MVP 的适配器顺序

适配现有后端时，优先增加可测试的数据输入与证据输出契约，由演示脚本或 API 客户端调用，之后才接前端。不得为了演示把无身份认证的本地服务直接公开为真实健康数据服务。

1. `MockWearableAdapter`：固定种子、可重复回放，覆盖平常、运动后心率变化、睡眠减少、设备未佩戴、网络失败、权限撤回。页面显著显示「模拟数据」。
2. `ManualCheckInAdapter`：用户主动填写睡眠感受、精力、情绪和情境，可跳过；与设备观测分别储存，不把自报冒充传感器。
3. `FileImportAdapter`（有实际导出格式才做）：显示文件格式、字段映射和预览；按文件来源追踪，拒绝静默猜单位。
4. 单个真实来源：有 Oura 则做 OAuth 后端；有 Apple Watch/iPhone 则评估最小 iOS HealthKit 桥；Android 则先确认目标设备数据实际进入 Health Connect。

统一接口建议：`capabilities()`、`connect()`、`sync(cursor)`、`disconnect()`。`capabilities` 返回真实支持的指标、可读取历史、粒度和同步模式，不能靠前端写死「实时监测」。

### 3.2 标准观测字段

| 字段 | 用途 |
|---|---|
| `observation_id / source_record_id / source` | 幂等、溯源，区分 mock、手填和设备 |
| `metric / value / unit / method` | 指标、数值、单位、测量或汇总方式；不同 HRV 方法不能混用 |
| `start_at / end_at / timezone / received_at` | 区分发生时间、当地日期与收到时间，处理跨日和迟到数据 |
| `device_id_hash / source_version` | 换设备、算法升级时避免直接合并基线 |
| `quality / coverage / missing_reason` | `valid / insufficient / stale / invalid / unknown`；缺失值不是 0 |
| `consent_id / purpose / retention_until` | 绑定授权目的与保留期限 |
| `synthetic` | 模拟证据不能在真实用户视图悄悄变为真实结论 |

连接状态与数据状态分别保存。连接状态可为 `not_connected / connecting / connected / revoked / error`；数据状态可为 `no_data / partial / fresh / stale / unsupported`。HealthKit 的未知读取状态应保留未知，不能强行映射 `revoked`。

接入 QA：单位验证、时间戳合法性、重复 ID、跨源重复、覆盖率、异常值、时区变化、迟到更新、取消授权后的增量停止。模型不可自行修补缺测并当成实测值。

## 4. 个人基线：让变化可解释、可被纠正

按用户最新要求，模拟范围已扩展为睡眠、心率/HRV、呼吸/血氧/皮肤温度、活动及设备评分共 30 项，见 [模拟指标扩展规格](shenglei-wearable-metrics.md)。真实设备接入仍需逐项确认。核心变化分析区分测量方法、窗口和设备，评分只作设备估算展示。按相同情境比较，不将运动中心率和睡眠心率混为一个序列。

最终建议以 recent 之前的 14 个日历日、至少 10 个有效日建立基线；recent 为最近 3 个完整日、至少 2 个有效日；两窗口中位数作比较。此处参数是待验证的工程规则，不是 Oura 算法、医学阈值或临床标准。样本不足时显示「正在积累个人参考」，继续支持自我记录。

输出应以可检验的差值为主，例如「昨晚睡眠 5 小时 50 分，比过去有效 10 晚的中位数少 55 分钟」。先不要输出虚构的 0–100 心理健康分。如果用稳健偏离量，必须处理 MAD 为 0、样本不足、设备变化、持续生病等情境，并保持计算可重现。基线版本及所用观测 ID 应随结果保存。

建议结构：

```json
{
  "observation_ids": ["obs_101"],
  "baseline_version": "sleep_v1_2026-11-04",
  "comparison": {"metric": "sleep_duration", "delta_minutes": -55, "valid_days": 10},
  "interpretation_status": "needs_confirmation",
  "hypotheses": ["作息变化", "身体不适", "暂时不明"],
  "user_confirmation": null,
  "allowed_actions": ["ask_context", "offer_optional_checkin"]
}
```

Agent 的交互顺序：先描述观测，再询问「这和你自己的感受一致吗」，提供「不一致／刚运动／熬夜但心情不错／不想解释」等选项。纠正只改解释和策略，不能篡改原始测量。单次「因为运动」只绑定该事件；「以后运动后别推测我焦虑」才可作为经用户确认的可撤回偏好。

解释和用户感受发生冲突时展示二者，而不是判定用户「没有意识到自己的真实情绪」。纠正后下一次同类情境应减少无根据提醒，验收需要实际展示这一行为变化。

## 5. 安全支持：独立于情绪分数的状态机

下表为产品与工程提案，需要专业人员审阅后才适合真实用户使用；不是临床分诊工具。不用心率、睡眠或情绪分类单独判断危机。

| 状态 | 进入条件示例 | 允许的动作与退出规则 |
|---|---|---|
| `routine_support` | 日常倾诉、趋势讨论 | 常规对话，可选练习；SOS 入口始终可见 |
| `clarify_safety` | 含糊但值得关心的表达或用户主动表示很难受 | 简短关怀与澄清，不循环盘问，不从设备信号推导危险 |
| `urgent_real_world_help` | 表达明确当下危险；用户主动打开 SOS 直接展示资源，但打开动作本身不等于危险判定 | 立即显示人工/本地紧急支持入口，使用预先审阅文案；暂停角色扮演、成长任务和奖励机制；不等模型二次分类才给入口 |
| `safety_support` | 有安全支持需求但不属于明确当下紧急情境，或用户希望了解支持选项 | 显示适当的人工资源和经审阅支持内容；保留进入紧急支持的入口 |

上述四个名称对齐仓库 psychology-interface.md 的提案路由，当前不能声称已实现。另以独立字段保存 `contact_status` 与 `follow_up_status`，避免把联系过程误当风险等级：点击只能记为「已点击」，没有可靠确认不能写「联系成功」；用户愿意可约定跟进，不能因沉默、离开页面、心率恢复就标记安全。

需要将「无法判断」与「低风险」区分。规则触发、模型评估和用户自报均带来源与时间；模型超时或输出格式错误时，静态支持入口仍可用。用户否定某个含糊推断可以解除相应误报，但对于仍存在的明确危险证据，不能因一次否定就机械清零。

本地资源是一个可维护目录：地区、语言、服务对象、服务时间、官方来源、最近核验日期、失效状态。没有完成当地资源核验前，不上线凭记忆填写的电话号码。不要自动给家属、雇主或第三方发消息；「生成可编辑求助短句」与「发送消息」是不同权限。

## 6. Agent 联动与模块边界

盛蕾模块应提供**观测摘要、个人变化证据、安全状态和允许动作**，而不是在底层直接生成全部角色话术。上层 Agent 读取受限摘要，不需要拿到整段原始生理序列和全部私聊。

建议链路：

```text
适配器 → 标准化与质量门 → 基线/变化计算 → EvidenceEnvelope
                                                   ↓
用户表达 → 安全策略/状态机 → allowed_actions → 对话 Agent → 回复检查
用户纠正 → CorrectionEvent → 本次解释更新 + 经确认的偏好更新
```

`EvidenceEnvelope` 建议含：`evidence_id`、`source_type`、`time_window`、`freshness`、`quality`、`observations`、`baseline`、`uncertainties`、`user_confirmed_context`。不要用单一 confidence 数字掩盖数据质量、解释不确定性和安全状态的区别。

安全策略在模型前控制允许动作，在模型后检查是否出现诊断口吻、未经证据支持的因果解释、虚构联系人或承诺已求助。模型不可通过 prompt 注入覆盖权限与安全状态。当前拟议心理接口的 `memory_update=null`，因此首步先保存会话内 CorrectionEvent 并证明下一轮行为更新；持久记忆写入必须作为后续明确开发项。仓库已有请求结果缓存，因此本轮就需测试纠正/撤权后的依赖失效；跨会话长期记忆另行开发。

## 7. 隐私与数据用途（本项目要求，不代表法律合规结论）

- 默认不将私人聊天、可穿戴数据、风险事件或用户纠正自动送入训练集。个人记忆、产品分析、评测与训练分别定义用途和授权，不能用「同意服务」一次打包。
- 推理与训练不同。即使自家不训练，调用第三方模型前也要核验其数据保留、训练使用、日志与地区条款；没有核验不能写「绝不留存」。
- Demo 使用合成或主动授权的脱敏样本；风险回归集人工编写，测试人员不需要读取真实用户危机聊天。
- 模型端只传必要摘要；令牌仅后端加密储存；日志默认不记录聊天正文、健康数据及 OAuth secret。
- 断开连接、停止同步、删除历史、删除派生记忆是不同操作，在界面解释清楚。删除需要覆盖特征、向量记忆、缓存、导出与备份生命周期；不能只删聊天列表。
- 如未来研究使用数据，需独立、可撤回、用途具体的流程。本稿未评估中国个人信息保护法、跨境处理或医疗器械监管的适用性，不以工程设计替代专项审查。

## 8. 研发节奏与验收

以下是调研阶段的工作包顺序，不代表从 11 月 4 日起仍有 15 天。实际中期与后续排期以开发方案第 14 节为准，真实设备不在必交范围。

| 时间 | 盛蕾交付 | 验收证据 |
|---|---|---|
| D1–D3 | 数据契约、mock 适配器、质量状态、合成样本 | 相同输入稳定输出；模拟标识贯穿展示、日志和摘要 |
| D4–D6 | 个人基线、差值摘要、冷启动和缺测处理 | 可手算案例通过；不同方法/设备不混算 |
| D7–D9 | 用户确认与纠正事件、Agent evidence 接口 | 同一运动场景纠正前后行为发生可解释变化 |
| D10–D12 | 安全状态机、静态资源入口、失败兜底 | SOS 不依赖模型可用；未完成联系不误报成功 |
| D13–D15 | 一条真实来源可行性验证，或明确保持 mock；端到端演示与问题单 | 真实授权/真实设备/真实响应分别提供证据；未完成的标记为未验证 |

建议建立小而明确的验收矩阵：

1. 数据测试：空数据、缺 3 天、重复同步、时区切换、秒/分钟混用、设备变更、过期数据、权限取消、401/429/超时、refresh token 并发刷新。
2. 基线测试：历史不足不输出判断；参考不泄漏当日；异常日不会悄悄填成正常；手算的差值与系统一致。
3. 情境测试：运动后信号变化但自报开心；睡眠减少但主动庆祝；设备显示恢复但用户明确求助。第三种必须由用户表达决定支持流程。
4. 纠正测试：局部纠正不成为永久人格标签；同类未来提醒遵循已确认偏好；删除偏好后不再引用。
5. 安全测试：直接求助、隐晦表达、引用小说、第三人称描述、否定句、玩笑语境、prompt 注入、模型失联、资源失效；关注漏触发、过度触发及处理路径，不只统计分类准确率。
6. 隐私测试：跨用户隔离、撤回权限、删除派生记忆、日志脱敏、训练管道默认无用户私密数据。
7. 产品验收：记录用户是否理解数据来源、能否纠正、纠正后建议是否更合适、提醒是否打扰；不以留存时长或对 AI 依赖程度作为唯一成功指标。

测试结论分层记录：A=合成数据/单元与状态测试；B=Web 端交互；C=真实账号授权与 API；D=真实设备连续数据；E=真实用户使用评估。完成 A/B 不得写成 C/D/E 已完成，更不能写为临床有效。

## 9. 可直接发给团队的短版

盛蕾先做「身体信号变化—用户确认—纠正后调整建议」的可演示闭环：统一数据结构，mock 跑通，真实设备作为后续候选；个人基线只做有证据的变化比较，不从心率直接认定情绪。安全支持独立做状态机，SOS 一直可用，模型失败也能显示人工支持入口，不把点击求助当成已获救。Agent 接收精简证据和允许动作；私聊、健康数据和纠正默认不进入训练。验收分别标注模拟、网页、真实 API、真实硬件和用户验证。

### 补充：Oura Advisor 的个人化交互

官方说明其结合健康指标与语言模型，用户可自选启用，并查看或删除记忆。适合借鉴数据使用选择与记忆管理；不据公开功能推断其内部算法。对应本项目的启用授权、可纠正理解和独立删除流程。[S10]
